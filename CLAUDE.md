# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

AI Job Copilot: a Python 3.11+ (3.13 recommended) CLI that searches job portals, scores postings against the user's profile, tailors a resume PDF per job with Gemini, applies (review, hybrid or auto mode), and emails a daily Excel report. It supports the `naukri`, `indeed` and `linkedin` portals (Playwright, one shared Chrome, run in parallel) plus an offline `sample` portal; InstaHire, new-project approvals, recruiter emails and profile sync described in README.md are roadmap items, not implemented.

## Commands

Windows environment; the venv lives in `.venv`.

```powershell
.venv\Scripts\activate
pip install -r requirements.txt
playwright install chromium

python main.py check                              # validate config, Gemini key, SMTP
python main.py run --source sample --no-email     # full pipeline offline on data/sample_jobs.json
python main.py run                                # real Naukri run (needs `python main.py login naukri` once)
python main.py review | apply --max 5 | jobs --status pending_review | report --send | rescore
python main.py import-resume resume.pdf         # draft profile from a resume PDF -> config/profile.imported.yaml
python main.py import-resume --apply            # promote the reviewed draft to profile.yaml (backup kept)
python main.py chat | ask "..."                   # Gemini agent driving the MCP tools
python main.py mcp                                # MCP server over stdio (also: python -m job_copilot.mcp_server)
python main.py -v <cmd>                           # debug logging

pytest                                            # all tests (tests/test_core.py; uses tests/fixtures/profile.yaml)
pytest tests/test_core.py::test_guard_blocks_invented_skills
```

## Architecture

- **Entry points**: `main.py` → Typer app in `job_copilot/cli.py`. CLI commands import heavy modules lazily inside each command. `mcp_server.py` exposes the same operations as MCP tools; `gemini_agent.py` spawns that MCP server as a stdio subprocess and hands the `ClientSession` to google-genai as a tool (automatic function calling).
- **Pipeline** (`pipeline.py`) is four LangGraph `StateGraph`s behind plain async functions (`process_posting`, `discover`, `apply_approved`, `run_daily`), so CLI/MCP/API callers are unchanged. `POSTING_GRAPH`: analyze (skipped when a stored analysis is passed in) → score (+ `resume_builder.resume_gaps`: matched must-have skills the base resume's summary/projects/experience never show) → (filter_out | approve_base: hybrid mode and no gaps, `APPROVED` with no tailored PDF since Naukri applies with the resume on the user's Naukri profile | tailor + Honesty Guard → render PDF → save as `PENDING_REVIEW` (hybrid reason names the gaps), or `APPROVED` in auto mode). `DISCOVER_GRAPH`: rescore (jobs `FILTERED_OUT` with a `score …` reason, still fresh, are re-scored locally from their stored analysis; those that now pass run `POSTING_GRAPH`; also `python main.py rescore` / MCP `rescore_jobs`) → search (each role × location query asks for a share of `search_card_target`; `Portal.keep_paging` pages on until the page cap, the target, or a page that adds fewer than `min_new_cards_per_page`; cards then sorted best-first by `matcher.prescore`) → triage (optional: one batched LLM call per portal re-ranks the cards before any page is opened, `triage: off|rank|filter`; no LLM, a failed call or an unreconcilable reply falls back to the prescore order, and a card the model did not score is never dropped) → pick (blacklist / `tracker.is_known` dedupe / `exclude_title_words` / `min_salary_lpa` floor / freshness check on the search card) → fetch (`portal.fetch_details` + freshness check on the job page) → process (runs `POSTING_GRAPH`) → pick … until the limit. `APPLY_GRAPH`: plan (enforces `max_applications_per_day` and `per_portal_cap`) → apply_portal, repeated per portal. `DAILY_GRAPH` = discover → (apply in auto and hybrid modes, `AUTO_APPLY_MODES`) → report (emailed; lists auto-applied jobs and jobs waiting for review). `Settings.mode` is `review | hybrid | auto` (Literal, validated). Nodes return state updates (never mutate state); per-run objects (tracker, llm, portal, settings) go in `config["configurable"]`; the discover loop sets a high `recursion_limit` because LangGraph's default of 25 steps is too low.
- **Scoring** (`agents/matcher.py`, deterministic): mandatory-skill credit is weighted per skill (`skill_weight`: named in the title or repeated in the JD weighs more) and reduced when the JD asks for more years of a skill (`SkillRequirement.min_years`) than `Skill.years`; nice-to-have and experience only count when the JD states them (weights renormalised, never a free 100%); no skills at all scores 0, fewer than 4 scales the score down; `role_fit` (title vs `preferences.roles` + skill words) has three tiers: 1.0 on-role or a generic title, `ROLE_FIT_FAMILY` for an engineering title in a stack you don't list ("Java Developer"), 0.0 for another line of work; it multiplies by `score_weights.role_floor` when below 1. `prescore` = half `role_fit` + half `card_evidence`, which uses the portal's tags when there are any (a tag you lack is real negative evidence, so it can reach 0) and otherwise the card `snippet`, which may only promote a card, never sink it (a truncated preview proves nothing by omission). `agents/salary.parse_lpa` reads "3-6 Lacs PA" / "₹5,00,000 P.A." / "₹30,000 a month"; an unstated salary always passes, because "Not disclosed" is the Indian default. `score_job` takes the posting for title/description. The offline `heuristic_analysis` splits the JD into required / nice-to-have sections and demotes tags the text never mentions.
- **Agents** (`job_copilot/agents/`) are plain functions. `SkillBank` (built from `profile.yaml` skills/aliases plus derived forms: "Name (ABBR)" also matches ABBR and Name, "React.js" also "React"; learning goals tracked separately) is the canonical skill lookup used by the analyzer, matcher and guard.
- **Computer-use agent** (`agents/cua.py`): opt-in via `apply_engine: cua` in settings (default `script`). After Apply opens the Naukri screening drawer, Gemini (Interactions API, `computer_use` tool, 0-999 coordinates) drives the page from screenshots; `execute_action` maps actions to Playwright and is the safety boundary: step cap `cua_max_steps`, host must stay naukri.com, `navigate`/back/forward excluded, any `safety_decision` confirmation stops the run (never auto-confirmed), and `type` only accepts text returned by the `lookup_answer` tool, which is backed by `agents/screening.answer_question` (profile facts only). No answer -> stops with `NEEDS_MANUAL`. Falls back to the scripted drawer handler when the key is missing. Preview feature: test on one approved job first; screenshots are saved in `storage/cua/`.
- **Honesty Guard** (`agents/honesty_guard.py`) is the core safety invariant: every LLM-tailored `TailoredContent` passes through `guard()`, which drops skills not in the bank, reverts (never "fixes") summaries/project rewrites that introduce unverified JD skills or exceed `max_keyword_repeats`, and only allows rewriting `on_resume` projects. Any new path that writes resume/profile content (including the MCP `update_project_description` tool) must go through these checks. Experience and education are read-only.
- **PII redaction** (`llm/redact.py`) is the second safety invariant: with `redact_pii: true` (default) `get_llm()` wraps every provider (Ollama too) in `RedactingLLM`, which masks the profile's name (and name parts), email, phone, location (and its parts except the country), LinkedIn/GitHub/portfolio and project URLs, plus any generic email/URL/10-13 digit phone, as `[KIND_n]` placeholders before a prompt leaves the machine, and restores them in the reply (every string field of a JSON result). The placeholder map is per call and in memory only; a reply with a placeholder that was never sent raises. On github/gitlab/bitbucket/linkedin links only the username is masked so the model can still tell links apart. The importer adds the resume's first line via `mask_also` (the name isn't in the profile yet). MCP `get_profile_summary` and `profile://yaml` use `profile_for_llm` (no `personal`, no project `github`). Any new LLM call must go through `get_llm()`; `agents/card_triage` does, and sends a narrow candidate block (roles, locations, years, skill names, learning goals) rather than `profile_for_llm`, so no `personal` data is in the prompt at all. Not covered: CUA screenshots and `chat`/`ask` (Gemini called directly with the user's own question and tool results).
- **LLM optional, provider-neutral**: agents take `llm: LLM | None` (`llm/chat.py` Protocol with `generate_json(prompt, PydanticModel)` / `generate_text`). `llm/factory.get_llm()` picks the provider from `LLM_PROVIDER` in .env (`auto` = first configured of Gemini key, Groq key, `OLLAMA_MODEL`; or `gemini|groq|ollama|none`). `llm/gemini.py` wraps google-genai and authenticates with `GEMINI_API_KEY` or a Vertex AI service account (`GOOGLE_APPLICATION_CREDENTIALS`, JSON kept in git-ignored `secrets/`; `GEMINI_BACKEND=auto` prefers Vertex; location defaults to `global`); Groq and Ollama share `ChatCompletionsLLM` (OpenAI-compatible `/chat/completions`, JSON mode + schema in the prompt, one validation retry). `llm/providers.py` holds the read-only checks behind `python main.py check` (Groq key/models, downloaded Ollama models). `chat`/`ask` and the CUA stay Gemini-only. When no provider is configured, functions receive `llm=None` and fall back to heuristics (`heuristic_analysis` in jd_analyzer, reorder-only tailoring in resume_builder) — keep that fallback working since tests and `--source sample` rely on it.
- **Portals** (`portals/base.py`): abstract `Portal` with `search`, `fetch_details`, `apply` (returns `(JobStatus, reason)`), used as a context manager; raise `PortalBlocked` on captcha/denial. Register new portals in `get_portal()` and `BROWSER_PORTALS`. Browser portals subclass `portals/browser.ChromePortal` (CDP attach to the shared debug Chrome with a hard `CONNECT_TIMEOUT`, **own off-screen window** via CDP `Target.createTarget(newWindow)` matched back by target id, live-view registration, `BLOCKED_TITLES` check, close; plus `on_login_page`/`is_logged_in`/optional `login`) and the generic `interactive_login` / `login_session`. **Portals run in parallel**: a module-level session count means only the last session to close quits Chrome (and then waits until it has exited, `wait_until_down`); `ensure_chrome` is serialized by a thread lock and relaunches once if a dying Chrome swallowed the first launch. A background tab would stop rendering, which is why each portal gets a window, not a tab. `live_view` keeps one page per portal (`set_page(portal, page)`); `/api/browser/status` lists active portals (and `viewing`) and `/api/browser/ws?portal=` streams one of them; `POST /api/browser/open {job_id}` opens a stored job's URL in its portal's window (`ChromePortal.show`) for the user to read or take over, holding that portal busy until `POST /api/browser/{portal}/close` or 15 min; `POST /api/browser/open-chrome {job_id}` (`browser.open_in_chrome`) opens it instead in a normal on-screen window of the copilot's Chrome for the user (any status, no live view, no busy claim). Chrome is never quit while such a user page is showing (`user_pages`), and `hide_from_taskbar` only touches the parked off-screen windows; `backend/busy.py` lets different portals run at once but returns 409 for the same portal twice (search, apply, login). `pipeline.discover_many` runs portals with `asyncio.gather` (re-score once first, guarded by a per-loop lock; one failing portal is reported, not fatal); `APPLY_GRAPH` splits the daily cap between portals up front, then applies per portal in parallel. LangGraph runs sync nodes (LLM calls) on worker threads, so one portal's LLM call doesn't stall the other. **Indeed** (`portals/indeed.py`, base `portals.indeed.base_url`, default in.indeed.com): search with `fromage` (cards show no dates, so `trust_search_age_filter: true` accepts undated postings; re-scoring counts their age from `created_at`), job page `[class*=simple-job-description]`; apply only via Indeed Apply (`[data-testid=viewjob-indeed-apply]`, may open its own tab, which is shown in the live view) walking contact -> resume -> questions -> review -> submit, answering only from `screening.answer_question`; company-site jobs, unanswerable questions, a step that doesn't advance, leaving indeed.com or the sign-in page all stop with `NEEDS_MANUAL`. Indeed has no automatic login (emailed code): log in through the live view. `run` defaults to `--source all` (every enabled browser portal, in parallel; `run_daily` returns `{"rescored": n, "<portal>": stats}`); the API's `/search` also accepts `all`. **LinkedIn** (`portals/linkedin.py`): search `/jobs/search/?keywords&location&f_TPR=r<seconds>` (+ `f_AL=true` when `easy_apply_only`, `f_WT=2` for Remote), results list scrolled so lazy cards render, selectors for both signed-in (`data-occludable-job-id`) and public guest (`.base-card[data-entity-urn]`) pages, dates from `<time datetime>`; apply only via Easy Apply modal (`NEXT` = Continue/Review/Submit by aria-label), unticks "Follow company", same stop rules as Indeed; `/checkpoint/` raises `PortalBlocked`; optional `LINKEDIN_EMAIL`/`LINKEDIN_PASSWORD` login tried once. `PortalSettings.daily_cap` (LinkedIn: 5) further limits a portal below `per_portal_cap` in `_plan`. Form questions for Indeed and LinkedIn go through the shared `portals/forms.answer_form` (profile facts only via `screening.answer_question`). CUA stays Naukri-only. Naukri uses a persistent browser session in `storage/browser/` and attaches over CDP (`connect_over_cdp`, `portals.naukri.cdp_url`) to a normal Chrome that `portals/chrome_debug.py` starts on demand (profile in git-ignored `storage/chrome-profile`, also `python main.py chrome`); it opens its own tab (then `hide_from_taskbar` marks Chrome's windows `WS_EX_TOOLWINDOW` so no taskbar button shows, while rendering and screenshots keep working), and `close()` closes that tab and then quits that Chrome through CDP `Browser.close` (`close_chrome_on_finish`, default true; set false to keep it running). It and registers its page in `portals/live_view.py`, which the web UI uses: the `/api/browser/ws` WebSocket (CDP screencast out, mouse/keyboard in, Origin-checked) behind the interactive `BrowserView` panel ("Take control" for OTP/captcha). The UI's "Log in to Naukri" / "Log in to Indeed" (`routers/login.py`, `/api/login/{portal}` -> `browser.interactive_login`) opens the login page in that browser, optionally tries typed-in details once (`SecretStr`, in memory only, never saved or logged), else waits while the user logs in via the live view; search/apply return 409 while it runs; when `apply` hits "Login to apply" it calls `NaukriPortal.login()` with `NAUKRI_EMAIL`/`NAUKRI_PASSWORD` (`config.get_portal_credentials`), at most once per session, and falls back to `NEEDS_MANUAL` on OTP/captcha.
- **Persistence**: `db.py` `Tracker` is a single SQLite `jobs` table (`storage/tracker.db`). Job id = sha1(portal:external_id); cross-portal dedupe uses a `fingerprint` of normalized company+title. Pydantic models passed as kwargs to `upsert_job`/`update` are JSON-encoded into the `*_json` columns, and any column in `JSON_COLUMNS` comes back decoded with the suffix stripped (`tags_json` → `row["tags"]`). `CREATE TABLE IF NOT EXISTS` runs on every open and never adds a column, so columns added after the first release go in `ADDED_COLUMNS` and `_add_missing_columns` ALTERs them in. `upsert_job` writes `tags`/`posted_text` only when the posting has them: `ON CONFLICT … DO UPDATE` copies every listed column, so an unconditional key would let a re-score (which rebuilds the posting from the row) erase what the search found. `is_known` takes `forget_filtered_after_days`, after which a `FILTERED_OUT` row stops blocking a re-post; every other status blocks for good. Status lifecycle is `JobStatus` in `models.py`.
- **Resumes**: `templates/resume.html.j2` rendered with Jinja2, printed to PDF via Playwright Chromium; each PDF gets a sibling JSON "vault" file (job, analysis, guard report, diff) in `storage/resumes/`. The resume URL is currently a local file link.
- **Resume import** (`agents/profile_importer.py`, `import-resume`): pypdf text + hyperlink URLs -> Gemini -> `ResumeExtract` -> `verify_skills` drops any skill not literally in the PDF text -> `merge_into_profile` keeps `preferences`/`equivalents`/`learning_goals` and never infers skill years. Writes a draft first; `--apply` promotes the (user-edited) draft. No offline fallback and no MCP tool by design: it rewrites locked sections, so it is user-run only.
- **Config** (`config.py`): `config/profile.yaml` is the single source of truth for the user's data; `config/settings.yaml` is validated into `Settings`. `get_settings()` is `lru_cache`d, `get_profile()` is deliberately not (the agent can edit project descriptions at runtime via `save_profile`). All timestamps use the fixed `IST` timezone.
- **Async Playwright only**: portals, `html_to_pdf`/`build_resume` and `pipeline.discover`/`process_posting`/`apply_approved`/`run_daily` are `async` and use `playwright.async_api`. CLI commands wrap them in `asyncio.run`; MCP tools `await` them. Don't reintroduce `sync_playwright`, because it fails inside the MCP server's event loop.
- **Logging goes to stderr only** — stdout is reserved for the MCP stdio protocol; never `print` to stdout from code reachable by the MCP server.
